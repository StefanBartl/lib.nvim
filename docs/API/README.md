# lib.nvim API reference

A function-signature-level index of every module `lib.nvim` currently
ships, split by topic. This complements [`../modules.md`](../modules.md),
which is a higher-level one-line-per-module namespace index with links out
to each module's own `README.md` — start there for "what exists and where
do I read more"; come here when you want to scan actual function
signatures across a whole theme without opening dozens of files.

Generated by reading every module's source and/or `README.md` directly
(139+ leaf modules across `lib.lua.*` and `lib.nvim.*`). Where a module has
its own `README.md`, that's noted inline as "(see README)" — treat this
document as a map, and the linked READMEs as the authoritative usage docs
with worked examples.

## Files

- **[foundations-lua.md](foundations-lua.md)** — `lib.lua.*`: strings,
  tables, functional helpers, JSON/YAML/UUID, time/date, numeral
  conversion, diff/dump/error handling, lazy-require, memoization. No
  dependency on the `vim` global anywhere except one flagged exception.
- **[filesystem.md](filesystem.md)** — `lib.nvim.fs.*`: working-directory
  management, root/project detection, path resolution, stat checks,
  directory creation/scanning, ignore lists, file read/write/mutation,
  opening files and URLs. The single largest namespace (28 submodules).
- **[cross-platform.md](cross-platform.md)** — `lib.nvim.cross.*`: OS
  detection, executable/Mason lookup, clipboard, open-with-default-app,
  reveal-in-file-manager, path separator normalization, WSL path
  conversion, file mutation/locking, and three tiers of process spawning
  (shell-string, argv-only, libuv-direct).
- **[ui-windows-buffers.md](ui-windows-buffers.md)** — `lib.nvim.buf_win_tab.*`,
  `lib.nvim.window.*` (including the `ui.kit` toolkit — ~19 themed UI
  primitives), `lib.nvim.notify.*`, `lib.nvim.selection`,
  `lib.nvim.terminal`, `lib.nvim.buffer.*`.
- **[commands-and-infra.md](commands-and-infra.md)** — `lib.nvim.usercmd`
  and the **`composer`** subsystem (the most widely-used module in the
  library — 30+ consuming plugins), plus `autocmd`, `map`, `dotrepeat`,
  `debounce`, `deps`, `treesitter`, `store`, `logger`, `progress`,
  `harvest`, `git`, `net.curl`, `lua_ls`, `cache`, `core`, `normalize`,
  `require`, `safe_api`, `system`, `token`, `neotree`.

## Conventions used throughout

- `(see README)` — the module has its own `README.md` next to its source
  with usage examples; this reference only lists signatures.
- `(no README)` — extracted directly from the source file's doc comments
  and exported functions; no separate narrative doc exists yet.
- A module documented as `return function(...)` (rather than `M.foo(...)`)
  means the module **is** a single callable — `require("...")` gives you
  the function directly, not a table to index into.
- Namespaces prefer real signatures (`fun(bufnr: integer): boolean`) taken
  from each source file's `---@param`/`---@return` annotations where
  present; a bare parameter list means the source had no such annotations.

## Known gaps / follow-ups noted while compiling this

- **`lib.nvim.buf_win_tab`**: `windows_utils.lua`'s `collect_all_state()`
  calls `M.only_nonfile_listed_buffers()`, and a sibling `Command-List.md`
  documents a `lib.nvim.buf_win_tab.neotree` unit — neither exists anywhere
  in the tree. Looks like stale documentation or a missing implementation;
  worth a follow-up to either implement it or remove the dead reference.
- A handful of modules mix concerns across namespace boundaries — e.g.
  `lib.lua.strings.convert.hex_to_string` calls `vim.fn.nr2char` despite
  living under the editor-independent `lib.lua.*` tree. Flagged inline in
  [foundations-lua.md](foundations-lua.md) rather than silently glossed over.
